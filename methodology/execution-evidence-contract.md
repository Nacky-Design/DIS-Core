# DIS — Execution Evidence Contract v0.1 (пилот)

**Цель:** разорвать возможность выдавать «сделано/проверено» без указания **какой артефакт, против какой версии обязательного правила, каким наблюдением проверен**. Дополняет Skill Execution Standard, UI Kit Gate и Visual Quality Gate; **не создаёт новые художественные этапы**.

## Контракт на каждый значимый production checkpoint
1. **Source preflight:** определить `project/scope`, актуальную задачу, approved baseline (путь + hash/version), UI Kit (путь + version), применимые HARD правила (ID, источник, scope, исключения). Нет источника — `not_verified`, не импровизировать числовые токены.
2. **Action proof:** указать точный файл результата и версию/hash; после последней правки заново проверить hash.
3. **Independent check:** необходимые автоматические проверки: обязательный текст/структура, фактический DOM/компьютед CSS, интерактивные сценарии, mobile; доказательства должны относиться к **той же версии** файла. Нет проверки — `not_verified`, а не PASS.
4. **Human review:** отдельный художественный статус `proposed` / `approved_by_user`; никакая цифра или автоматический тест не устанавливает художественное одобрение.
5. **Delivery gate:** ссылка только на проверенную версию HTML; краткое описание реальных изменений. По умолчанию не генерировать PNG/ZIP/PDF для anonymized internal pilot A2 без явного запроса.

## Обязательные поля данных
`rule_id | source@version | scope | requirement_class(HARD/JUDGEMENT/EXPERIMENT) | expected_condition | exception_policy | artifact@sha256 | verification_method | evidence_ref | status | human_decision`.

`PASS` допускается только при подтверждении соответствующей проверкой и свидетельством. `evidence_ref` к неподлинному или непросмотренному файлу **не доказывает** прохождение теста. Локальный пилот валидатора для наличия файлов — только ранняя стадия, без browser guarantee.

## Классы проверки
- Машинно определимые: путь/версия, отсутствие/наличие точно заданного текста, числовые токены с **проектной** таблицей, URL/файлы, ошибки JS, responsive overflow, семантическое состояние, сравнительные браузерные computed-style/diff.
- Экспертные: композиционный баланс, логика художественного синтеза, смысловая читаемость, соответствие характеру бренда, целостность сложной сцены.
- Смешанные: сверка состава/геометрии иерархий; компьютер собирает скриншот и метрики, арт-директор принимает смысл/характер.

## Composition Contract — ограниченный пилот
Для ключевой новой секции: **вопрос посетителя → главный тезис → связанные доказательства → композиционный фокус → маршрут чтения → поведение в mobile → переход к соседней секции**.
Не навязывать единую геометрию; чертёж и CSS сами по себе не доказывают композиционной убедительности.
Основание — рабочее обсуждение материала Ветрова, пересказанное в истории; исходный пост следует отдельно сверить, прежде чем приписывать ему данную формулу.

## Внедрение без ложной готовности
- v0.1: read-only validation manifest/hash/file evidence, локальные негативные тесты.
- v0.2: независимая браузерная генерация evidence и сверка настоящего UI Kit.
- v0.3: клиентский CI и required status checks, проверка отказов/ложных PASS.
До v0.3 нельзя называть систему принудительным блокирующим контролем рабочего проекта. Блокирование CI реально лишь если check обязателен в настройках защиты ветки и нельзя бесконтрольно обойти его.
