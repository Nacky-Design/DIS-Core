# DIS — DEC-001 / Document-to-Execution Contract / строгая исполнимость решений

**Статус:** фундаментальный принцип DIS, принят автором 2026-11-05; внедрение как процедурный P0 для всех этапов и как программный fail-closed gate там, где исполнение идёт через контролируемый Controller. **Не утверждать**, что текст в репозитории перехватывает прямые вызовы ChatGPT image generation, Figma или браузерного Codex: для этого нужна реальная интеграция tool gateway.

## Главный инвариант — цитата автора и совместно принятого принципа

> **Ни один этап DIS не имеет права начинать производство на основании простого ознакомления с документами. Каждое применимое утверждённое требование должно быть перенесено в исполнительный контракт, а его выполнение — проверено на фактическом результате.**

Это **P0-инвариант**, распространяется на исследование, семантику, прототип, Art Direction, UI Kit, Frankenstein Selection, FA-01, FA-02, Visual Concept, Figma decomposition и реализацию в Codex. Повторяется в адаптированных к этапам формулировках, но не заменяется лозунгом: каждый этап обязан оставить проверяемый материальный след.

## Запреты (fail-closed)

1. `READ != COMPLY`: факт чтения документа, передача его пути, позитивная оценка модели или перечисление решений **не являются доказательством исполнения**.
2. `INPUT != OUTPUT`: наличие утверждённого UI Kit/референса в пакете не подтверждает, что он отражён в результате.
3. `INTENT != EVIDENCE`: описание художественной идеи и длинный генеративный промпт не заменяют проверку реального PNG/HTML/документа.
4. `SSA != PRODUCTION_GATE`: согласованный Stage Start даёт право **готовить** исполнительный контракт, но производство запрещено до `DEC_PRE_EXEC_PASS`.
5. `FAIL != IGNORE`: отсутствующий обязательный источник, неотображённое требование, конфликт, неподтверждённое исключение, критическое визуальное нарушение или устаревший hash означают `STOP_DEC_001`. Не «дорабатывать по вдохновению», не заполнять пробел фантазией и не отменять правило новым общим промптом.
6. `PASS != SRA`: технический/экспертный аудит соответствия не равен авторскому утверждению результата. Отдельное SRA-001 обязательно.

## Пять обязательных переходов

### DEC-01 / Source Validation
Загрузить **реальные байты и полные тексты** применимых источников, проверить документ, его версию, подпись/основание одобрения, статус и scope, доступность первичного ТЗ, актуальность UI Kit. Если файл недоступен, нельзя обозначать его «прочитанным». В реестре указывать точное `source_id` и хеш.

### DEC-02 / Requirement Extraction
Сформировать **полный применимый набор** требований; не выборочное резюме. Каждое требование имеет уникальный `requirement_id`, документ + якорь/раздел, `source_sha256`, статус и область, `LOCKED | GUIDED | OPEN`, `verification_kind` и критерий прохождения. Источниковые художественные свойства сохраняют отдельную запись на каждый референс. Гипотезы и предложенные параметры нельзя повышать в статусе. Важные исходные цитаты/смысл не переписывать в пользу привычных шаблонов.

### DEC-03 / Execution Mapping
Для **каждого активного утверждённого требования** задать `implementation_plan`: что конкретно появится в результате, что **не** появится, как будет доказано выполнение; отсутствие плана => STOP. `GUIDED` не означает «копировать пиксели»; требуется обозримое соответствие художественного приёма. `OPEN` допускает вариативность, но не переопределение `LOCKED`. Запрещены фиктивные записи «учтено», «по умолчанию», «смотри промпт», «TODO». Нужны фактические действия.

### DEC-04 / Pre-Generation / Pre-Execution Gate
Контроллер (или честно обозначенная ручная процедура при отсутствии подключённого gateway) сверяет: полный перечень наследованных требований, конкретный план, конфликтность, статус утверждений, зафиксированные `source_hashes` и `plan_hash`, согласованный scope и отсутствие запрещённых паттернов в плане/композиционном тезисе. При ошибке — `STOP_DEC_001`, никакого запуска инструмента производства. **В FA-01 художественная гипотеза может проверяться внутренне; отдельное авторское согласование необходимо при конфликте или настоящей неоднозначности, но не для каждого шага автоматически.**

### DEC-05 / Actual Artifact Compliance Audit
После исполнения проверяется **фактический** PNG, HTML, документ, Figma-слои или код в том же наборе `requirement_id`: `PASS | FAIL | NOT_CHECKED`, описание **наблюдаемого** доказательства и ссылка на конкретный результат/скриншот/тест. Критические `LOCKED` нарушения => `REJECTED`, никаких переходов к следующему этапу. `GUIDED` художественные критерии требует экспертной проверки и при необходимости решения автора; не выдавать их за машинно доказанные. При недоступности изображения/рендера ставить `NOT_CHECKED`, не `PASS`. Промпт не является доказательством внешнего результата.

## Исполнительный контракт (DEC Execution Ledger)

Живой машинно- и человеко-читаемый контракт **для конкретного проекта + stage + scope + snapshot**:

- Заголовок: `schema=DEC-001/v1`, `project`, `stage_id`, `scope`, `pcs_snapshot_sha256` (или явно `snapshot_unavailable` до полного Python компилятора), `stage_prompt_sha256`, `source_inventory`.
- `requirements[]`: `id`, `source_id`, `source_path`, `source_sha256`, `source_anchor`, `approval_state`, `scope`, `lock`, `criterion`, `implementation_plan`, `verification_kind`, `severity`.
- Не смешивать выбранные художественные свойства с черновыми общими пожеланиями. Добавленные автором указания получают отдельный источник и приоритет по правилам DIS.
- `pre_execution`: только `PENDING | PASS | STOP`, с конкретными доказательствами. Никогда не записывать `PASS` на основании одной просьбы модели.
- `artifact_audit`: проверка **после** появления настоящего результата с объектными ссылками на доказательства.
- Версии и хеши contract/источников/промпта фиксируются; любое изменение входов сбрасывает текущий `DEC_PRE_EXEC_PASS` и SSA snapshot.
- Вопросы автору только при действительно необходимом содержательном выборе; автоматические проверки не перекладывать на пользователя.

### Псевдопротокол исполнительного инструмента

```text
validated = PCS.validate_all_sources_and_approvals()
if not validated: STOP_PCS_PREFLIGHT
ledger = DEC.extract_from_full_sources(validated)
if missing_required(ledger) or missing_mapping(ledger): STOP_DEC_001
if conflicts(ledger) or stale_hashes(ledger): STOP_DEC_001
if not DEC.check_pre_execution(ledger, concrete_plan): STOP_DEC_001
artifact = controlled_production(concrete_plan)  # only if route is actually gated
audit = DEC.inspect_real_artifact(artifact, ledger)
if audit.critical_failed or audit.not_checked_critical: REJECTED
present_proposed_result_for_SRA_001()
```

## Проверяемость и реальное ограничение технологий

- **Repo/Controller:** можно проверять хеши, IDs, полноту mapping и статусы в автоматических тестах. Машинная полнота полностью зависит от полноты реестра требований: сам Python не понимает весь смысл исходных документов без специально проведённой экстракции и её ревью.
- **Художественный результат:** компьютер не может объективно доказать «качество по Fin» одним флагом. Доказательство — инспекция фактического изображения + сопоставление с property-specific constraints + авторское решение.
- **ChatGPT/Figma:** непосредственные tool calls пока НЕ перехватываются. Пока DEC в чате — обязательный процедурный STOP; **не обещать гарантированного аппаратного/программного запрета**. Для жёсткой защиты нужна tool gateway / CI branch protection / scoped credentials.
- **Восстановление ошибки:** сохранять отклонённую попытку и разбор в исходном контексте следующего варианта. Не менять автором одобренные принципы ради получения удобного PASS.

## Как правило повторяется на этапах

| Этап | Тот же принцип, адаптированный к работе |
| --- | --- |
| Discovery | Каждое исходное утверждение связано с первоисточником, гипотезы помечены и в отчёте есть evidence |
| Competitive Research | Каждый переносимый приём имеет проверенный референс, границы применимости и статус |
| Semantic Architecture | Каждая смысловая договорённость имеет исходный факт/гипотезу, фиксированный scope и место в архитектуре |
| Prototype | Каждый обязательный пользовательский сценарий реализован в конкретном состоянии и маршруте, затем проверен |
| Art Direction | Каждое принятое художественное свойство разложено на воплощаемые композиционные механизмы |
| UI Kit | Каждый утверждённый токен/роль предъявлен в реальном specimen, а не в одном только описании |
| Frankenstein | Каждое выбранное свойство отдельно индексировано, но в итоге не превращается в буквальный коллаж |
| FA-01 | До изображения составлен проверяемый композиционный контракт; после — проверка настоящего изображения |
| FA-02 | Все принятые секции и связи сверены с контрактами; нельзя «потерять» решения при сборке страницы |
| Visual Concept | Каждая финальная композиция проверена по прежним решениям и фактическому рендеру |
| Figma decomposition | Каждая смысловая и художественная инварианта сохраняется в слоях/компонентах, с diff и проверкой |
| Codex implementation | Код, responsive, взаимодействия и рендер проверяются относительно принятой Figma/PNG; изменения объяснены |
