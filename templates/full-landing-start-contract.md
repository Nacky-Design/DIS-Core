# DIS — Start Contract полного лендинга (шаблон)

**Статус:** заполнить при старте проекта; черновик не становится утверждённым автоматически.  
**Методологические опоры:** [приоритет инструкций](../methodology/instruction-precedence.md) · [целостность страницы](../methodology/full-landing-continuity.md) · [маршруты](../methodology/production-routing.md) · [mobile-first](../prompts/mobile-first-design.md).

## 5. Рабочий цикл и контроль
- Следующий этап / ближайшая **системная проба**: […]
- Для каждого блока: вход по контракту → mobile + desktop → проверка связи с соседями → интеграция в общий preview → обновление решений.
- Before showing Visual Concept: [Visual Quality Gate](../methodology/visual-quality-gate.md) — пилотный порог 7/10, не ниже, без критических дефектов; 8/10 только ориентир: […].
- Before approval: Decision Readiness + [UI Kit Gate](../methodology/ui-kit-gate.md). Before showing revision: Concept Integrity. Before delivery: Release/QA.
- Статусы **решения**, **артефакта** и **проверки** вести раздельно.
- Финальная page-level проверка до объявления результата завершённым.

## 5a. Reference Engine и Decision Dialogue

- Reference Routing: `REUSE | PARTIAL_EXPLORE | EXPLORE`, причины: […]. При EXPLORE отдельно записать независимые межотраслевые поисковые запросы.
- Reference Depth evidence: реальное число inspected и глубоко разобранных, незакрытые механизмы/непроверенные состояния: […].
- Passive capture: `auto_capture_verified | manual_checkpoint_capture | persistence_failed | not_connected` — **не** выдавать методику за работающий collector.
- Значимая развилка для пользователя (при наличии): `decision_id / stage / compatible option ids[] / chosen_option_ids[] / human approval scope`. Несколько совместимых направлений выбираются одновременно.
- Применимый Skill Contract: [standard](../methodology/skill-execution-standard.md), QA-case refs, статус фактического выполнения: […].
## 6. Минимальные метрики пилота
- Возвраты к принятым решениям, причины: […]
- Несохранённые тексты/функции и разрывы между блоками: […]
- Ошибки responsive/mobile: […]
- Стоимость/сложность передачи в выбранный инструмент: […]
- Ошибки версии/релиза, дополнительное время на QA: […]

**Порядок работы:** заполни то, что действительно известно; не требуй всё перед началом независимой части работы. Не подменяй реальные источники выдуманными фактами. Не создавать новый документ на каждом шаге — вести этот контракт вместе с коротким решением проекта.
