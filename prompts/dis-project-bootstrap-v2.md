# DIS — Universal Project Start v2.0 · ALPHA
**Статус:** действующий стартовый промпт DIS v2 Alpha для новых тестовых проектов. Прежний [Bootstrap v1.0](dis-project-bootstrap-v1.md) сохранён для проектов, закреплённых на v1. Alpha не гарантирует независимую авторизацию или перехват прямых инструментов.

Начинаем новый проект по **DIS — Design Intent System**.  
Методология: the provided DIS Core package (methodology/dis-master-process-v1.md)  
Репозиторий **этого клиентского проекта**: [укажите ссылку GitHub]  
Прилагаются доступные исходники клиента: ТЗ, КП, брендбук, презентации, ссылки, медиа, референсы.

**СЕЙЧАС выполняй только Bootstrap / Intake / Project Configuration. Не начинай Discovery, генерацию, HTML или Figma до допуска.**

1. **Подключение.** Прочитай действующие контракты DIS из GitHub, включая AGENTS.md, PCS-001, DEC-001, STG-001, HCA-001, действующие классификацию, исследовательские стандарты, Stage Start/Result, UI Kit и визуальные QA. Проверь версии и статус. Не считай этот candidate утверждённым автоматически. Если нет репозитория клиента, помоги создать/подключить его; без проверенного доступа не выдавай стадии за утверждённые.
2. **Состояние.** Если репозиторий уже содержит проект DIS, сначала восстанови историю и активный этап из GitHub (RECOVERY), не обнуляй принятые решения. Для нового проекта зафиксируй доступные источники и факты/гипотезы, не публикуй конфиденциальные исходники в публичный репозиторий.
3. **Классификация.** Определи тип продукта, задачи бизнеса и аудитории, структуру, неопределённости, риски, исходные ограничения. Раздельно предложи **Research Scope** (что изучаем), **Design Scope** (что создаём визуально: HERO-only или главную/другие согласованные шаблоны) и **Delivery Scope** (какие артефакты в конце нужны). Исследовать разрешено весь продукт, даже когда дизайн ограничен главной.
4. **Варианты маршрута.** Предложи **несколько** осмысленных альтернатив (Express / Guided / Strategic / Reference-Led, допустимые комбинации). Покажи охват, обязательные проверки, открытые гипотезы и последствия. Дай аргументированную рекомендацию, **но не выбирай автоматически «минимально достаточный» маршрут** и не навязывай полный процесс.
5. **Конфигурация модулей.** По исходникам предложи, что включить и в какой глубине: Discovery/конкурентов/JTBD/интервью, IA/семантику/прототип (с выбором формата до производства), свои или найденные референсы, Art Direction, шрифты, Seed UI Kit, motion, SEO, контент, ассеты, mobile, технологические ограничения, итоговые файлы. Объясняй новичку смысл выбора простыми словами, не задавай лишнюю анкету.
6. **Discovery/NMT.** Если проекту нужен AJTBD/рынок, проверь реальную доступность Codex skills Ивана Замесина из https://github.com/zamesin/Next-Move-Theory-Canon-and-Skills и условия лицензии; новый продукт → nmt-market-research, действующий → nmt-diagnose, реальные интервью → nmt-analyze-interviews, методологическая навигация → nmt-chat. Не объявляй skill запущенным лишь по ссылке; не копируй лицензируемые тексты в проект без прав. DIS DBR-001/RQC-001 действуют.
7. **Показ решения.** Представь оператору **одну рекомендованную конфигурацию и понятные альтернативы**, список существующих и отсутствующих источников, точный текущий статус и первую контрольную точку; подготовь **Stage Start Packet**, не запускай следующий этап без явного SSA.
8. **Дальнейший обязательный цикл.** Каждый этап: загрузка утверждённого из GitHub → работа/итерации → проверка результата → предложение «Углубить / Доработать / Утвердить этап» → явное авторское утверждение **конкретной версии** → подтверждённая запись в GitHub → следующий Stage Start Packet. Не путай формальную запись и реально доверенную авторизацию; если контроллер не подключён, сообщай NOT_ENFORCED.
**Официальная команда перехода:** когда оператор пишет **«Переходим к следующему этапу»**, **не** запускай новый этап автоматически и **не** считай фразу утверждением. Прочитай активный этап и статус из GitHub, проведи Stage Exit Check по заранее согласованным критериям, покажи структурированный итог решений, источников, гипотез и проверок. При незакрытых обязательных критериях предложи доработку; при готовности — **«Углубить / Доработать / Утвердить этап»**. После отдельного авторского утверждения версии запиши и проверь GitHub; затем подготовь следующий Stage Start Packet, а производство начинай только после отдельного SSA/DEC. Если предыдущий этап уже APPROVED и запись проверена, сразу подготовь пакет следующего без повторного утверждения. Неизвестное состояние — STOP, не додумывай из чата.

9. **Путь к концепции.** По выбранной стратегии и Scope переходи через необходимые исследования, структуру/прототип, референсы, Art Direction, Seed UI Kit и **Creative Synthesis Packet**. Первый полноценный визуальный результат — HERO. Если выбрана главная, развивай её **по отдельным секциям** из утверждённого HERO и UI Kit с Full-Page Review; ядро DIS завершено на утверждении концепции.
10. **Финальные файлы.** После финального авторского утверждения подготовь только выбранные Deliverables (например, Research, UI Kit, Reference/AD rationale, концепцию, handoff); используй реальные решения и источники, не выдумывай причины постфактум.

**Сейчас:** зафиксируй только результат начального анализа и представь несколько маршрутов с рекомендацией. Оператор выбирает Scope, стратегию и первый этап. Не объявляй результат \`APPROVED\` на основании текста модели.
