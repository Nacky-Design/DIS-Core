# DIS — Reference Evidence & Calibration Protocol · pilot v0.1

**Статус:** рабочая методология согласована 25.10.2026; результативность пока не измерена. **Область:** Reference Research → Art Direction → Visual Concept → Visual Quality Gate → Retrospective.

## 1. Один контур знаний, две функции

**Reference Library:** записи о внешних проектах, редакционных тренд-гайдах, собственных работах и антипримерах. Назначение — находить и применять уместные приёмы. **Calibration Benchmarks:** подмножество записей, по которым есть достаточно предметных свидетельств, чтобы сравнивать конкретные аспекты художественного качества собственной работы.

Запись может быть полезным референсом, не став эталоном; отсутствие премии не дисквалифицирует сильную работу. **Никаких переносов внешних баллов Awwwards в 0–10 DIS** и никаких премиальных баллов за «похоже на тренд».

**Выбор из отобранного:** [Divergence → Curated Choice](divergence-curated-choice.md) дополняет Reference Research: DIS исследует широко, предлагает арт-директору 2–3 лучших **отличающихся** решения после Quality Gates. Сохраняем не только победителя, но и проверяемые причины, почему сильные альтернативы проиграли, в качестве будущих калибровочных свидетельств.
## 2. Типы источников — не эквивалентные рейтинги

| Сигнал | Что можно утверждать | Чего нельзя утверждать |
| --- | --- | --- |
| Жюри/профессиональная награда | Указанный конкурс признал работу по опубликованным критериям на указанную дату | Что она решает нашу UX-задачу или все аспекты UI лучше |
| Behance Featured / curated | Работа прошла редакционный отбор | Что количество appreciations — профессиональный рейтинг |
| Views / appreciations / соцпопулярность | Относительный интерес/охват в контексте платформы | Объективный художественный балл |
| Тренд-гайд/прогноз | Редакция или исследователь выделил направление в заданный год | Что конкретный сайт качественен или приём обязателен |
| Проверенный live-продукт | Конкретные интерфейсные/поведенческие факты при фактической проверке | Что любые ненаблюдаемые сценарии реализованы |

Для каждого источника хранить авторство/организатора, дату материала, дату проверки, тип утверждений (обзор/прогноз/оценка/проверенный интерфейс), URL, охват, ограничения, достоверность и доступность артефакта. По награде Awwwards фиксировать категорию/срез, год и число **именно если опубликованы и проверены**.

### Trend Radar (годовой слой)

Ежегодный guide — **сигнал актуальных приёмов и художественных гипотез, а не гарантия качества**. Исследовать 2–4 разных первичных источника с обозначенной редакционной перспективой, отдельно наблюдаемые тренды и прогнозы. Для каждого тренда: формулировка, год, пример реального применения, бизнес/UX-задача, адаптация для mobile, реализуемость, срок актуальности, риск поверхностного копирования. Не объявлять тренд «мировым стандартом» по одному посту.

Перед стартом крупного нового проекта или при обновлении направления пересматривать актуальность; не навязывать календарную ревизию каждой CSS-итерации. Старые тренды архивировать, **не стирать**. Если нет доказательства распространения, статус `single-source hypothesis`.

## 3. Поток знаний: одна работа — два результата

1. **Discover:** искать подходящие примеры по задаче и смысловым модулям; включать профессионально признанные и нишевые.
2. **Verify:** фиксировать внешний сигнал отдельно от собственной оценки; изучить реальный вид/интерактив при возможности.
3. **Extract:** описать *конкретный приём*, действие, композицию, содержательную роль, сильные стороны и ограничения.
4. **Apply:** использовать только подходящую гипотезу в текущем проекте; зафиксировать где, почему и что проверили.
5. **Save:** добавить/обновить карточку в единой [библиотеке](../references/library/README.md), без параллельных PDF. Текущей проектной задаче полезен `analysed_reference`.
6. **Promote:** в `calibration_benchmark` переводить только карточку с подтверждённым внешним основанием и собственным предметным разбором по **конкретным применимым осям**. Не присваивать UX/код/адаптив, если просмотрены лишь кейс-изображения.
7. **Feedback:** после внутренней оценки и арт-ревью записывать собственную оценку DIS, реальную оценку/комментарии человека, расхождения и причины. Антипримеры сохранять как обучающие свидетельства, но не как отрицательные «вечные запреты».

**Основание для promotion к эталону:** видны фактические композиции/состояния; внешнее признание верифицировано *или* есть убедительное обоснование профессиональной экспертизы; описаны достоинства и слабости по именованным осям; контекст и ограничения обозначены; неизвестные аспекты не оценены. Число лайков и попадание в тренд не достаточны.

## Межотраслевой перенос — до оценки близости

**Не использовать семантическую/отраслевую близость как фильтр на этапе первичной насмотренности.** Даже если внешний проект решал совсем другую исходную задачу, его геометрия, движение, ритм или механизм взаимодействия может быть преобразован в решение задачи клиента. Сначала широко изучить варианты и описать `observed_mechanism → proposed_new_function`, только затем оценить конечную пригодность. Этот обязательный для сложных художественных задач процесс: [Reference Depth & Analogical Transfer](reference-depth-analogical-transfer.md).

Дополнить карточки полями `original_domain`, `original_function`, `mechanism_abstraction`, `alternative_target_function`, `transformation_plan`, `observation_status`. Сильный межотраслевой аналог не обязан иметь высокой изначальной `task_relevance`: она оценивается **после попытки нового переноса**, вместе с доказательствами, а не заранее.

## 4. Reference Confidence — не магический рейтинг

Хранить три **разделённых** суждения: `external_recognition`, `task_relevance`, `transferability` (high/medium/low/unknown с причинами). Не вычислять фиктивные веса. При равной уместности внешняя экспертиза помогает приоритизировать глубокий разбор, но не заменяет его. **На стадии wide search рейтинг task_relevance не является барьером: сначала проверить скрытую/межотраслевую переносимость.** После переноса конечная семантическая уместность и применимость могут перевесить престиж награды или исходное отраслевое сходство.

## 5. Две независимые проверки качества собственного дизайна

**Gate 1 / Baseline Compliance — PASS/FAIL.** До художественного рейтинга проверить соответствие принятым текстам/смыслам, UI Kit, фактическую мобильную читабельность, функциональные действия в пределах этапа и отсутствие очевидной сырости. `FAIL` → внутренний возврат, независимо от художественной оценки. При статичном концепте не требовать production-функций, но явно указывать границы проверки.

**Gate 2 / Art Quality — экспертная шкала 0–10.** После PASS отдельно оценить: художественная идея, типографика/ритм, смысловой UX, UI/предметность, целостность, применимое mobile/состояния. **Минимум показа 7/10**, целевой ориентир 8/10. Эталонные референсы помогают обосновать сравнение конкретных аспектов, но не присваивают балл по аналогии. Оценка DIS — калиброванное экспертное мнение, не машинно объективная метрическая истина. Никакой формальной средней для скрытия слабых осей; применимые критические слабости блокируют.

**Цикл:** Visual Concept → Compliance → Art review с доказательствами → `needs_work` / `ready_for_approval` → человеческое решение; `approved_by_user` только по явному согласию человека. Факт показа/скоринг не означает утверждения.

## 6. Калибровка оценок

Для версий с реальной человеческой оценкой фиксировать `DIS score + scope + critical findings` → `human score/comments` → `gap and why` → `revised interpretation / anti-pattern` → следующий контроль. **Не подгонять исторические баллы и не повышать самооценку ради порога.** Человек может дать словесный вердикт без числа: сохранять слова, не выдумывать число.

После накопления сопоставимых примеров можно обсуждать эталонные диапазоны 5/7/8/9, но без притворства, что они универсальны для всех жанров. Виды работ (медицинский продукт, промо, fashion, B2B) требуют отличающихся критериев уместности; применимость фиксируется по факту.

## 7. Границы, синхронизация, связь со стилем

Одна библиотека и один индекс, отдельные записи `trend_signal`, `analysed_reference`, `calibration_benchmark`, `our_accepted_work`, `anti_example`. Значимая запись может иметь несколько ролей, но критерии доказательности не подменяются.

Самостоятельный анализ и пополнение в активных задачах. GitHub — **на checkpoint**, в соответствии с принятым C/purpose/checkpoint для UI Kit; это параллельный ритм, **не автоматическое продвижение художественных решений**. Нет фонового мониторинга и автозагрузки новых ссылок без задачи.

Найденные приёмы могут питать [Studio Signature](studio-signature-evolution.md), но **внешний референс и авторский почерк студии — разные объекты**. Паттерн становится кандидатом на собственный стиль только после авторской трансформации и уместного применения, не при сохранении ссылки.
