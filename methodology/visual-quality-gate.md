# DIS — Visual Quality Gate · pilot v0.1

**Статус:** обязательное правило внутреннего показа для пилотов DIS; численный порог — экспериментальная калибровка, не объективный измеритель качества.  
**Решение:** anonymized internal pilot / медлендинг, 25.10.2026. **Текущий порог: ≥7/10; 8/10 — желательная цель, НЕ обязательный порог.** Пересмотр порога только после явного решения пользователя и анализа пилотов.

**При нескольких обоснованных художественных направлениях** применяем [Divergence → Curated Choice](divergence-curated-choice.md): широкая внутренняя генерация, отдельная проверка кандидатов двумя gates и показ **2–3** реально различных сильных решений. Не дополнять состав третьим слабым решением ради квоты. При конкретной локальной правке полный конкурс не требуется.
## Когда запускаем

- После содержательной проверки и применения актуального UI Kit — **перед первым художественным показом Visual Concept / нового дизайн-направления или существенной переработки**.
- Для локальных изменений — проверяем затронутые критерии и регрессии, не проводим масштабный конкурс референсов при каждой CSS-правке.
- Для Research, Prototype, открытых UX-гипотез и экспериментальных технических проб не требуем художественную оценку по этой шкале: стадия ясно обозначается.
- Явная просьба показать *сырую пробу* допускает показ ниже порога, но только с меткой `exploratory_not_ready`, без приглашения утвердить её как готовый дизайн.

## Правило выхода

**Общая оценка не ниже 7/10** и **нет критических дефектов** по смыслу, утверждённому контенту, ключевому действию, мобильной читабельности, системной типографике или откровенно сырому UI. Не маскируем провал по существенному критерию усреднением: ориентир — ни один применимый критерий ниже 6/10. Если хуже — `needs_work`: агент самостоятельно дорабатывает, а не передаёт арт-директору для поиска очевидных ошибок.

Оценка **экспертная**, а не автоматический «измеритель вкуса». Балл без указания конкретных достоинств и дефектов не является свидетельством качества. Высокая оценка от DIS **не равна** `approved_by_user`. Человек принимает существенное художественное решение отдельно.

## Оцениваем по шести осям (0–10, только применимые)

| Ось | Контрольный вопрос |
| --- | --- |
| **Художественная идея** | Есть ли самостоятельная композиция и читаемый главный акцент, а не украшенный wireframe? |
| **Типографика и ритм** | Выдержаны ли иерархия H2/H3/body/UI, опорные оси, масштаб, переносы и воздух? |
| **Смысл / UX** | Понятно ли, что происходит и зачем; нет ли дублей, лишних переключателей, ложных связей? |
| **UI и компоненты** | Выглядят ли интерфейсы правдоподобными и законченными по устройству, состояниям и действиям? |
| **Целостность продукта** | Совпадает ли язык с соседними утверждёнными секциями и актуальным UI Kit без слепого повторения композиций? |
| **Mobile-first / реализация** | Проверены ли необходимые mobile и desktop состояния, доступность управления, отсутствие переполнений? |

Если измерения не проводились, писать «не проверено» вместо придумывания доказательств. Весовой рейтинг без согласованной калибровки не использовать: итог — обоснованное профессиональное суждение по совокупности осей с фиксацией слабейшего звена.

## Два независимых gate и калибровка

**Gate 1 / Baseline Compliance (PASS/FAIL):** проверяет согласованный контент и смысловую логику, типографию и компонентную совместимость с UI Kit, применимые сценарии/мобильную читабельность и отсутствие очевидной сырости. `FAIL` всегда означает `needs_work`, без «компенсации» баллами художественности. Не требовать реализованной серверной функции от концепт-изображения; границы проверки указывать явно.

**Gate 2 / Art Quality (0–10):** проводится после PASS. Сохраняет шесть художественных осей данного документа, экспертную аргументацию, текущий порог **≥7** и цель **8**. Ни премии референсов, ни тренд-гайд 2026 не дают автоматической прибавки к баллу DIS. Калибровочная библиотека используется только для **предметного сопоставления проверенных свойств**, в сочетании с человеческим арт-ревью и разбором расхождений. Подробности: [Reference Evidence & Calibration](reference-evidence-calibration.md).

**После ревью:** записать собственную оценку DIS, дословную/числовую оценку человека (если она была), причины расхождения и конкретное изменение критериев. Если человек высказал только качественные замечания, не выдумывать число. Даже PASS + ≥7 не означает `approved_by_user`.

**Вопросы арт-директору:** при содержательной художественной развилке, требующей человеческого выбора, применять [Decision Dialogue](decision-dialogue.md) с возможностью выбора нескольких совместимых направлений. Принятые предпочтения сохранять в [Studio Learning](../skills/studio-learning/skill.md), но не считать локальное утверждение глобальным Studio Signature. **Проверка semantic graph integrity и mobile semantic continuity обязательна, когда это и есть функция концепции**, даже если JS/overflows технически исправны.
## Preflight агента

1. Сверить точный исходный контент, смысловую логику, ограничения и последнее принятое решение.
2. Взять актуальный **[UI Kit](ui-kit-gate.md)**; проверить роли типографики, компоненты, адаптив и допустимые исключения.
3. Для существенной новой художественной задачи пройти [Reference Depth Gate](reference-depth-analogical-transfer.md) **перед дорогой визуальной композицией**: показать реально осмотренный широкий межотраслевой массив, механизмную карту неочевидных переносов и глубокий разбор лучших кандидатов; не принимать один красивый пример за завершённое исследование. При локальной технической правке полный поиск не повторять.
4. Оценить фактический результат в реальном масштабе вместе с соседними блоками и на мобильном. Для HTML — открыть состояния в браузере, не оценивать только CSS.
5. В существующем журнале решений записать: `version · 6 scores/NA · overall · blocking defects · changes · evidence · readiness`.
6. При `needs_work` самостоятельно выполнить локальный цикл «дефект → исправление → повторная проверка». Если **две содержательные** итерации подряд сохраняют ту же композиционную/смысловую проблему, признать возможный `research_gap` и адресно вернуться к поиску/аналогическому переносу, вместо третьего косметического варианта. Не подменять улучшение новым абстрактным описанием.

**Пример записи:** `VC-07.1 · typography 5 / UI 3 / mobile 7 ... · overall 5/10 · needs_work · H3 конфликтует с заголовком сцены; карточка пациента — схематичная; повторная проба требуется`. Цифры в примере — иллюстративны, не результат новой проверки.

## Границы

- Никаких гарантированных «90% попадания», автоматического самоподтверждения и искусственного завышения баллов ради прохода.
- Блокировка художественного показа не должна задерживать независимую работу над контентом и логикой; не выдавать внутренний прототип за финальный визуал.
- Один обновляемый журнал решений проекта, не отдельный PDF на каждую итерацию.
- Применять вместе с [Decision Readiness](decision-readiness.md), [Concept Integrity](concept-integrity.md) и [Design System Continuity](design-system-continuity.md).
