# DIS — Reference Engine: Passive Accumulation, Maturity & Routing · v1.0

**Решение:** 26.10.2026. **Статус:** спецификация согласованной системы; фактический collector/MCP/index ещё не подключены — статус автоматизации `specified_not_implemented`. Части межотраслевого анализа и Quality Gates существовали ранее. [Skill Standard](skill-execution-standard.md) · [Library](../references/library/README.md).

## 1. Двенадцать механизмов и их место

| № | Механизм | Владелец-скилл | Проверяемый результат |
|---|---|---|---|
| 1 | Cross-Domain Research | Reference Intelligence | Широкий межотраслевой просмотр, доказанные источники |
| 2 | Reference Depth Gate | Reference Intelligence | `sufficient_to_synthesize` или `research_gap` с предметным основанием |
| 3 | Analogical Transfer | Reference Intelligence | Исходная функция → механизм → новая функция → трансформация |
| 4 | Frankenstein Synthesis | Visual Synthesis | Самостоятельные целостные композиции; provenance механизмов |
| 5 | Passive Reference Accumulation | Reference Memory | Проверяемая запись каждого события исследования, не декларация |
| 6 | Reference Engine | Reference Memory | Индексированные записи/поиск/дедупликация/связь с проектами |
| 7 | Maturity Gate | Reference Memory | Подсчёт зрелости + проверка качества поисковой выдачи |
| 8 | Reference Routing | Reference Memory | `REUSE`, `PARTIAL_EXPLORE`, `EXPLORE`, обоснование |
| 9 | Anti-Echo Chamber | Reference Intelligence | Независимый внешний поиск по исходной проблеме |
| 10 | Divergence → Curated Choice | Visual Synthesis | 2–3 различимые сильные концепции или честный `needs_work` |
| 11 | Two Visual Quality Gates | Visual Synthesis | Compliance PASS/FAIL + обоснованный Art score, без фиктивного PASS |
| 12 | Studio Signature Evolution | Studio Learning | Контекстный реестр гипотез, оценок и только явных approvals |

Распределение ответственности не означает четыре изолированных агента. События исследования одновременно потребляются Reference Intelligence и сохраняются Reference Memory.

## 2. Накопление — без лазейки «по возможности»

**HARD:** каждое фактически выполненное исследовательское действие создаёт запись/событие `research_event`. При обнаружении URL сохранять `discovered`; реально осмотренный экран → `visually_inspected`; разобранный механизм → `analysed`; применение к проекту → `applied`; человеческое решение → `reviewed`. Не повышать статус без доказательства; хранить источники и дату обращения, версию страницы/возможные изменения.

Событие содержит `event_id · run_id · project_id · source_id · kind · occurred_at · observed_by · evidence_refs[] · result · persistence_status`. Отсутствие видео/скриншота не компенсировать утверждением «проверено». URL и аналитические выводы сохранять с происхождением, изображение — только по правам источника. Событие повторно применимо без дубля по `event_id` (идемпотентно).

**Если запись недоступна:** не ставить `saved`, обеспечить повторяемую очередь/локальный durable log при её наличии; иначе `persistence_failed` и `checkpoint_not_complete`. Нельзя делать вид, что автоматизация есть, пока поиск реально не маршрутизирован через сборщик. До внедрения — существующий GitHub checkpoint с явным `manual_checkpoint_capture`; это не равняется автоматическому захвату всех действий.

## 3. Два слоя знаний, один индекс

- **Exposure layer:** широкий поток уникальных кандидатов и осмотренных референсов; не удалять непобедившие источники, но убирать ложные дубли.
- **Applied learning layer:** механизм, его перенос, применение, human feedback, результат, anti-example, approved_scope.

Разделить запись-источник и найденный механизм; один источник может содержать несколько механизмов, один механизм — подтверждаться многими источниками. Связать `source → mechanism → transformation → project_decision → review`. Рейтинги из Awwwards и иных внешних источников не выдавать за баллы нашей работы.

## 4. Maturity Gate — строго, но без запрета раннего REUSE

С первого источника включены **накопление** и **точечный recall**. Полноценный самостоятельный поиск по внутренней библиотеке — только если **все** условия:

- ≥150 уникальных реально визуально осмотренных референсов (`visually_inspected` и выше, но не `discovered`);
- ≥8 представленных отраслей / художественных контекстов (не путать домены URL с отраслями);
- ≥20 **содержательно различных** описанных механизмов с доказательствами (не просто 20 тегов);
- ≥15 глубоких разборов с исходной функцией, наблюдаемым механизмом, возможным новым назначением, ограничениями;
- в пяти разноплановых тестах поиска ≥4 показывают несколько **содержательно разных** подходящих механизмов по явному критерию с записанным проверяющим.

Все пороги — **экспериментальные числа пилота, не закон дизайна**. Оценивается `maturity_library_global`, отдельно `coverage_for_this_task`. Зрелая в среднем библиотека может не покрывать сложную частную задачу. Отдельный `our_accepted_work` допускает REUSE до 150 при всех условиях соответствия.

## 5. Routing: строгое дерево решений

**Шаг 0:** назвать новую задачу/подзадачу и неизменяемый contract. **Шаг 1:** краткий Internal Recall: доказанные прошлые решения и ограничения; это не финальный художественный отбор.

**Шаг 2:** разрешить `REUSE` без внешнего поиска ТОЛЬКО если все условия:
(а) та же функция и сравнимые сценарии; (б) применимые состояния/mobile проверены; (в) UI Kit/бренд и действующий scope соответствуют; (г) отсутствуют открытые существенные дефекты; (д) есть человеческое утверждение в требуемой художественной области. Любое неизвестное ключевое условие → `PARTIAL_EXPLORE` либо `EXPLORE`, не произвольное REUSE.

**Шаг 3:** `PARTIAL_EXPLORE`, если определённый функциональный компонент можно повторить, но появились новые художественные/предметные требования: наследовать только проверенную часть, внешний поиск по новому конфликту обязателен.

**Шаг 4:** `EXPLORE` при новом значительном художественном замысле, новой механике, непокрытой ключевой функции, двух содержательных повторных неудачах или необходимости пересмотреть прежнюю модель. Внешний межотраслевой поиск **обязателен и независим** от shortlist внутренней библиотеки.

**Шаг 5:** после внешнего исследования сравнить новые и внутренние решения на равных, выполнить перенос/синтез; при материальной художественной развилке — [Decision Dialogue](decision-dialogue.md). Новизна сама по себе не преимущество; очевидно пригодный утверждённый компонент не перерисовывать ради исследования.

**Шаг 6:** сохранить каждое новое исследовательское событие и итог выбора; checkpoint не закрывать с немаркированным `persistence_failed`.

## 6. Anti-Echo Chamber: порядок без самозамыкания

Сначала **короткий** Internal Recall, но для `EXPLORE` список известных референсов НЕ используется как семя внешней поисковой выдачи. Запросы строятся из исходной проблемы, требуемого визуального поведения, иных отраслей/функций. Зафиксировать `independent_search_queries` **до** сравнения с внутренним shortlist. Внешние кандидаты потом сопоставить с внутренними по применимости, не по происхождению.

Без доступа к внешним источникам писать `external_search_not_verified`, не выдавать старые записи за новые находки; не ставить `Reference Depth PASS` на основании выдуманного разнообразия.

## 7. Триггеры отказа от очередной косметической итерации

Две содержательные версии с той же неустранённой смысловой/композиционной проблемой → `research_gap_review` и адресный поиск. Локальные багфиксы, изменение одного токена и полировка не считаются самостоятельной содержательной версией.

## 8. Контроль реализации

Текстовый skill spec ≠ подключённая автоматизация. Для `auto_capture_verified` обязателен реально исполняемый collector, воспроизводимая запись каждого поддерживаемого события, тесты идемпотентности/дублей/сбоев, индекс, проверенный поиск и интеграция с фактическим Research-маршрутом Codex/ChatGPT. Пока этого нет, честный статус `specified_not_implemented`.
