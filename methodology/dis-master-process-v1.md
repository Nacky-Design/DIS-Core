# DIS — Master Process v1.0
**ID:** DIS-MPA-001 · **Дата:** 2026-11-25 · **Статус:** DIS v2 ALPHA / AUTHOR-REVIEWED METHOD; техническое enforcement ограничено подключёнными контролируемыми маршрутами.  
**Назначение:** единый маршрут DIS от ТЗ до утверждённой дизайн-концепции. **Не объявлять действующей системой принуждения**, пока маршрутизатор, GitHub approval controller и обязательные проверки не реализованы и не испытаны.

## 0. Сущность DIS и граница продукта
DIS — **Design Intent System**: управляемая методология работы оператора с ChatGPT, Codex и другими инструментами. DIS определяет альтернативные стратегии разработки, объясняет решения, сохраняет историю и проверяет последовательность. Оператор руководит исследованиями, UX, арт-дирекшном и передачей результата. Модель не подменяет клиентские факты, реальных пользователей, профессиональную экспертизу и авторское утверждение.

**Конечная точка ядра DIS:** утверждённая дизайн-концепция в согласованном Design Scope: **HERO-only** либо **HERO → главная страница, секция за секцией**. HTML, Figma, frontend, CMS и полный продукт — выбираемые производственные/передаточные маршруты, а не обязательная часть ядра. Для локальной правки **существующей** утверждённой концепции повторный HERO не нужен: применяется LOCAL_PATCH.

**Инвариант:** каждый новый этап наследует действующие применимые утверждённые решения из GitHub проекта; использование документов доказывается результатом, а не фразой «изучено».

## 1. Необходимые условия запуска
1. Новый пользователь передаёт имеющееся ТЗ/КП/брендбук/ссылки/референсы/ассеты; неполные вводные допустимы.
2. DIS загружает действующую ревизию центрального репозитория DIS, не предполагая, что знание методики встроено в модель. Отсутствующие источники — NOT_VERIFIED.
3. **Обязателен отдельный GitHub-репозиторий каждого проекта** (публичный или приватный). Доступ/права записи проверяются фактически. До подключения можно объяснять/помогать, но нельзя сообщать об утверждённых в DIS этапах.
4. Для существующего проекта — **RECOVERY**, не чистый старт; при расхождении записей и чата авторская запись в GitHub приоритетна после проверки.
5. Версии методики и проектных документов закрепляются ссылками/commit SHA; обновление центрального DIS не переписывает действующий проект автоматически.

## 2. Три независимых Scope
- **Research Scope** — исследуем одну область, главную, сайт или **весь продукт**, включая будущие сценарии.
- **Design Scope** — визуально проектируем HERO-only, полную главную или выбранные экраны/шаблоны.
- **Delivery Scope** — какие итоговые артефакты нужны: концепция, Research, UX, Reference/AD report, UI Kit, handoff, HTML/Figma/PNG/PDF и пр.

Пример: исследовать **весь магазин**, но создать концепцию **только главной**. Не сводить объём исследования к числу рисуемых экранов. Ограничения сроков, бюджета и достоверности источников демонстрировать отдельно.

## 3. Выбор стратегии (без автоматического «минимально достаточного» маршрута)
После классификации проекта по действующему [Project Classification](project-classification.md) DIS предлагает **несколько** допустимых маршрутов и одну аргументированную рекомендацию. Базовые **стратегии**, не уровни качества:
- **Express Concept:** быстрые проверяемые гипотезы/референсы → короткая смысловая схема → визуальный HERO; не выдавать предположения за исследованные факты.
- **Guided Design:** Discovery → структура/прототип → референсы → Art Direction → Seed UI Kit → HERO → выбранные секции.
- **Strategic Design:** весь бизнес/продукт, JTBD/альтернативы, IA, контент/SEO, сложные пользовательские маршруты и зависимости → концепция в выбранном Design Scope.
- **Reference-Led:** операторские референсы → разбор переносимых свойств → предметная валидация под бизнес/контент → концепция, с возможным расширением исследований.

Модули можно комбинировать; например Strategic Research + HERO-only Design + Figma Handoff. Для каждого варианта показать покрытие, неопределённости, ожидаемые результаты, потенциальную стоимость и последствия. Нельзя молча снижать применимый обязательный стандарт Discovery (DBR-001/RQC-001). Укороченный маршрут — явно согласованный scope, не тайный пропуск требований. **Выбор оператора обязателен и фиксируется до следующего этапа.**

## 4. Стартовая конфигурация: предложить, а не навязать анкету
DIS сначала извлекает из исходников известные значения, затем показывает проектную конфигурацию и предлагает изменить применимые модули: Discovery/глубина, конкурентный анализ, интервью, UX/прототип и формат, свои/найденные референсы, типографика, графика, UI Kit, motion, SEO, контент, адаптив, медиа, production route, стек, итоговые документы.

Новичок должен видеть смысл и последствия выбора простыми словами. Не задавать 15 независимых вопросов, если большинство решений можно обоснованно предложить. Не подтверждённые исходники отмечать как гипотезы. **Технологический стек:** на Intake фиксируем ограничения; после UX/IA формируем рекомендованную и запасную архитектуру с ограничениями по бюджету, CMS, поддержке, SEO и интеграциям; оператор вправе проконсультироваться с разработчиком и утвердить до зависимого производства.

## 5. Модель рабочего этапа — Stage Cycle
Каждый выбранный этап представляет повторяемый цикл:
1. **LOAD:** загрузить текущую \`.dis\`-запись GitHub и точные версии применимых утверждённых решений/артефактов.
2. **START:** собрать Stage Start Packet; получить SSA-001 для точного scope, когда требуется действующими контрактами; проверить DEC до производства.
3. **WORK:** исследования, варианты, спорные гипотезы, свободные уточнения, изменения внутри этапа. Разговор в сторону **не переключает** активный этап.
4. **CHECK:** DIS проверяет обязательную полноту, источники, качество, противоречия, фактические файлы/рендер и уровень неопределённости; критические пробелы устраняет либо объявляет BLOCKED.
5. **EXIT OFFER:** если готово, предложить **«Углубить» / «Доработать» / «Утвердить этап»** с рекомендацией и объяснением, что даст углубление.
6. **AUTHOR ACTION:** утверждение означает согласие с **конкретной версией и scope**, а не просто с последним сообщением.
7. **GITHUB COMMIT:** сохраняет артефакты, ledger, approvals, хеши и активное состояние. **Только после подтверждённой записи** этап \`APPROVED\`; иначе \`PENDING_SAVE\`.
8. **NEXT:** только теперь подготовить следующий Stage Start Packet. Начало следующего этапа требует отдельного разрешения, не автоматического перехода.

Статусы: \`IN_PROGRESS\`, \`NEEDS_WORK\`, \`BLOCKED\`, \`READY_FOR_AUTHOR_REVIEW\`, \`PENDING_SAVE\`, \`APPROVED\`; отдельно технический \`PASS/FAIL/NOT_CHECKED\` и авторский \`approved_by_user\`. Автоматический аудит **не** является согласием человека.

**Stage Anchor** читает активный этап из GitHub при каждом восстановлении чата/смене инструмента. После отвлечения DIS возвращает оператора к текущему этапу без навязчивого повторения статуса на каждом сообщении. Команда «сгенерируй следующий экран» без разрешения не меняет состояние.

**Reopen Stage:** после нового существенного требования создаётся новая ревизия; прежнее утверждение сохраняется; зависимые решения отмечаются NEEDS_REVALIDATION, а не переписываются молча.



### Canonical Transition Command — `NEXT_STAGE_REQUEST`

**Официальное текстовое намерение оператора:** **«Переходим к следующему этапу»** (и однозначные эквиваленты). Это **запрос Stage Exit**, не самостоятельное `approved_by_user`, не замена SRA-001/SSA-001 и не разрешение на производство следующего этапа.

**Детерминированная обработка по текущему GitHub-состоянию:**
- `IN_PROGRESS | NEEDS_WORK | READY_FOR_AUTHOR_REVIEW | BLOCKED`: запустить Stage Exit Check против утверждённых до начала этапа Acceptance Criteria. Подготовить Stage Exit Summary с (a) stage/версия/scope, (b) фактическими артефактами и проверками, (c) реестром **предложенных / выбранных оператором / отвергнутых / утверждённых ранее** решений, (d) гипотезами/валидационным долгом, (e) рекомендацией и объяснением возможного углубления.
- Критический `FAIL | NOT_CHECKED | BLOCKED` по применимому `REQUIRED`: **не** открывать author approval для завершения; предъявить пробелы и пути устранения. Не делать выдуманный PASS.
- Все `REQUIRED=PASS` и существенных blockers нет: статус `READY_FOR_AUTHOR_REVIEW`, предложить оператору **«Углубить» / «Доработать» / «Утвердить этап»**. Первые два удерживают активный этап; третье требует явного SRA для точного результата.
- `PENDING_SAVE`: повторить/проверить авторизованную GitHub фиксацию; пока нет подтверждения, не продвигаться.
- `APPROVED` с проверенной записью: повторное утверждение не запрашивать; подготовить Stage Start Packet следующего этапа. Начало работ — только через действующий SSA/DEC.
- Неизвестное/устаревшее/недоступное GitHub-состояние: `STOP_PROJECT_PREFLIGHT`, запросить восстановление, не выводить READY из содержания чата.

**Безопасность намерений:** команда может быть вызвана пользователем посреди длительного исследования и не обрывает его без показа итогового решения. Не считать её автоматическим согласием с предложенными решениями. Для естественно-языкового варианта с неясным смыслом («перейдём?», «что дальше?») предложить просмотр статуса/выходную проверку и не выполнять утверждение по догадке.

**Не путать** `NEXT_STAGE_REQUEST` (вызов exit flow), `AUTHOR_STAGE_APPROVAL` (явное принятие версии и scope), `NEXT_STAGE_START_AUTHORIZATION` (SSA для производства следующего этапа): это отдельные события с отдельными доказательствами. Не дублировать существующие SSA/SRA, а маршрутизировать команду через них.


### Откуда DIS знает, что этап готов — Stage Acceptance Contract

**Acceptance Criteria должны появиться ДО работы над этапом**, а не генерироваться задним числом при его завершении. Это не новый параллельный договор: требования записываются в существующий Stage Start Packet / DEC ledger, с привязкой к маршруту и версиям источников.

**Как составляется контракт:**
1. Взять обязательные требования **конкретного этапа** из актуальных DIS методик/контрактов (для Discovery — DBR-001/RQC-001, для прототипа — применимые UX/Prototype contracts, для визуала — UI Kit/Visual Quality/DEC и т. п.).
2. Взять **выбранные оператором** стратегию, Research/Design/Delivery Scope и активные модули. Простая стратегия не отменяет применимые обязательные требования тайно; сложный продукт может расширить критерии.
3. Добавить **требования клиента и наследованные утверждения** предыдущих этапов, включая запреты и открытые вопросы.
4. Сформировать **проверяемый список**: требование / зачем / обязательно ли для выхода из этапа / ожидаемый артефакт / метод доказательства / кто проверяет / последствия отсутствия.
5. Показать оператору **короткую понятную версию критериев** вместе со Stage Start Packet до утверждения старта. Не требовать от новичка вручную разрабатывать профессиональные критерии.
6. Заморозить критерии для текущего stage snapshot. Если изменилась задача или Scope — показать diff, заново согласовать затронутые критерии и зафиксировать новую версию. Нельзя подгонять критерии под уже созданный результат.

**Классы требований:**
- `REQUIRED` — обязательный результат или проверка для данной стадии и scope; отсутствие/провал препятствует READY.
- `JUDGEMENT` — профессиональная качественная оценка: агент показывает основания и ограничения, но не объявляет художественное принятие автоматически.
- `OPTIONAL/DEEPENING` — добровольное углубление, не препятствует готовности, если явным решением не стало обязательным.
- `DEPENDENT/UNKNOWN` — непроверенный факт с владельцем и назначенным следующим моментом проверки. Не все неизвестные блокируют завершение Discovery: блокировать только те, без которых невозможно ответственно перейти к **конкретному** следующему действию. Неизвестное нельзя выдавать за подтверждённый факт.

**Выходной аудит (Stage Exit Check):** сверить каждое `REQUIRED` с **реальным артефактом** (ID, версия/hash, ссылка на подтверждение), проверить противоречия, несанкционированные изменения и критические `DEPENDENT`. У каждого пункта `PASS / FAIL / NOT_CHECKED / BLOCKED` и указан метод (автоматическая проверка / источник / экспертная оценка). `NOT_CHECKED` не становится `PASS`. После содержательного изменения результата повторить затронутые проверки.

- `NEEDS_WORK`: обязательный пункт не выполнен; DIS сама исправляет доступное, затем проверяет снова. «Утвердить этап» не предлагается как разрешённое завершение.
- `BLOCKED`: объективно отсутствует необходимый источник/решение/доступ; DIS показывает одну конкретную причину и способ разблокировки.
- `READY_FOR_AUTHOR_REVIEW`: все применимые `REQUIRED` подтверждены, критических блокеров нет, экспертные суждения представлены оператору. Только теперь DIS предлагает **«Углубить / Доработать / Утвердить этап»** с собственной рекомендацией.
- `APPROVED`: автор принял точную версию, а GitHub-запись проверена. Техническая готовность не означает авторское одобрение.

**Пример — Reference Intelligence:** должны существовать реальный реестр изученных источников с наблюдениями, выбранные/отклонённые референсы и мотивы, переносимые свойства и ограничения, соответствие бизнес-задаче и ранее утверждённой визуальной логике, понятный результат для следующего Art Direction. Фиксированное число «не меньше десяти референсов» без обоснования **не критерий**. Если оператор запросил анализ анимаций, его объём становится частью версии scope; простой разговор об анимации сам по себе не завершает и не меняет этап.

**Условия READY — это проверяемое основание для предложения авторского решения, а не гарантия идеального качества.** Машинные проверки отвечают за измеримые критерии, экспертное суждение — за художественные и смысловые, окончательный выбор — за оператором. До реального GitHub-валидатора это остаётся процедурной спецификацией, не доказанным enforcement.

## 6. GitHub: проектная власть и структура
Рекомендуемая **проектная схема, подлежащая реализации**:
\`\`\`text
project-repo/
  .dis/
    project-state.json        # active stage; route; pinned DIS revision
    project-config.json       # Research/Design/Delivery scopes; selected modules
    decisions.json            # stable IDs, source, state, dependency
    stages/<stage-id>/        # drafts, final result, revision log
    approvals/<stage-id>/     # explicit user approval evidence, version, scope
    artifacts/                # source and generated assets or verified links
    evidence/                 # checks and rendered evidence bound to artifact SHA
  src/ ...                    # actual product output, where applicable
\`\`\`
Запись должна быть транзакционной с проверкой commit SHA/ожидаемой версии, конфликтов и повторной загрузкой состояния. GitHub commit или JSON \`approved: true\`, записанный самим агентом, **не доказывает волеизъявление** пользователя. Для доверенного approve нужен отдельный контроллер, связывающий действие оператора с конкретным immutable snapshot. Пока контроллер не развёрнут, явный диалог + GitHub log — лишь **procedural**, помечать \`NOT_ENFORCED\`; не имитировать кнопку или криптографическую подпись.

Разрешения SRA/SSA и журналы DEC/PCS/STG остаются действующими; эта модель **не вводит альтернативную систему авторизации**.

## 7. Полный маршрут (модули, не 18 обязательных отдельных согласований)

|---|---|---|---|
| 00 | Bootstrap & Repository Preflight | Проверить GitHub, DIS SHA, права, источники | активная проектная запись |
| 01 | Intake | ТЗ/КП/бренд/материалы; факты vs гипотезы | Source Register и brief |
| 02 | Project Configuration | предложить несколько стратегий, 3 Scope, модули, deliverables | принятый route snapshot |
| 03 | Discovery | бизнес, аудитории, Jobs, ценность, риски | исследование + гипотезы + долг валидации |

| 05 | Product & Content Strategy | оффер, позиционирование, контент, SEO-намерения | content direction и карта смыслов |
| 06 | Information Architecture | страницы, сценарии, навигация и продуктовые зависимости | IA / sitemap |
| 07 | Semantic Architecture | смыслы секций, CTA, доказательства, точный контент | семантический контракт |
| 08 | Prototype | **сначала выбор формата**, затем mobile-first UX/states | утверждённый прототип/структура |
| 09 | Reference Intelligence | свои/найденные/смешанные; причины и свойства выбора | selection + source trace |
| 10 | Art Direction | художественные принципы, композиция, референсы | AD decision |

## 9. End-of-stage / end-of-project artifacts
На каждой контрольной точке фиксируются **фактические рабочие результаты** (MD/JSON/PNG/HTML и др.), версия, источники, принятые/отклонённые варианты, обоснование, невалидированные гипотезы. После \`CONCEPT_APPROVED\` DIS предлагает **выбранные ранее** клиентские артефакты, например:
- Research & hypotheses report
- Semantic/UX/prototype rationale
- Reference / Art Direction report
- Consolidated UI Kit / motion specs

Финальные PDF/DOCX/презентации оформляются **по текущему утверждённому UI Kit**, не пересочиняются с нуля. Отчёты **должны отражать реальные записи решений**, а не постфактум выдумывать мотивы.
