# DIS — UI Kit Evolution Protocol · управляемая автономия (C)

**Статус:** согласованная операционная модель UI Kit для пилотов DIS; практическая эффективность ещё проверяется.  
**Решение пользователя:** 25.10.2026 — `model=C`, `promotion=purpose`, `repository=checkpoint`.  
**Связанные правила:** [UI Kit Gate](ui-kit-gate.md) · [Design System Continuity](design-system-continuity.md) · [Visual Quality Gate](visual-quality-gate.md) · [приоритеты и статусы](instruction-precedence.md).

## 1. Неизменные принципы

1. **Управляемая автономия (C).** DIS самостоятельно выявляет, создаёт, оформляет, исправляет и переиспользует компоненты *внутри принятого художественного контракта*. Существенное изменение утверждённой системы или художественного языка — решение арт-директора.
2. **По назначению (purpose), не по счётчику.** Потенциально повторяемый компонент можно включить в живой UI Kit с первого появления, когда его функция, границы, состояния и область применения понятны. Второе использование не требуется. Одноразовая авторская композиция не превращается в компонент автоматически.
3. **В GitHub — по checkpoint.** Изменения накапливаются в рабочей версии UI Kit/журнале проекта и фиксируются вместе на существенных контрольных точках. Не создавать обязательный коммит на каждый patch, экран или состояние.
4. **Готовность ≠ художественное утверждение.** `candidate`, `verified`, `reusable` обозначают рабочую зрелость. Только явно принятое человеком решение может получить `approved_by_user` в заявленном объёме; `verified` не означает `approved_by_user`.
5. **Система не подавляет творчество.** Новый блок наследует общие токены и компоненты, но может иметь собственную композицию. Намеренное исключение фиксируется и не становится автоматически глобальным токеном.

## 2. Где находится единый источник

В каждом проекте — **один** живой UI Kit как часть System/Page Design Contract, реализованный по выбранному маршруту (Figma, HTML/CSS, токены + демонстрация компонентов и т. п.), плюс **один** обновляемый журнал решений. Не нужно делать отдельный PDF или новый UI-kit на каждую секцию.

`Seed UI Kit`: после появления проверяемого художественного ориентира и до затратного масштабирования. Допускает `proposed` токены, но должен показывать реальные mobile/desktop типографические роли.  
`Consolidated UI Kit`: после художественного принятия базовой концепции, до производства множества секций/шаблонов. Подтверждает фактические роли и живые компоненты; содержит ссылку на исходную утверждённую версию.

Свойства `source-verified` и `exception` из базового UI Kit Gate — **происхождение** и **тип отклонения**; не подменяют отдельный статус художественного решения.

## 3. Цикл на каждом новом блоке

1. **Read:** загрузить актуальный System Design Contract, живой UI Kit, утверждённые соседние блоки, компонентный реестр.
2. **Reuse:** сопоставить функциональное назначение и состояния с имеющимися компонентами; сначала пробовать существующий.
3. **Classify:** (а) повторно используемый системный паттерн, (б) допустимая вариация существующего, (в) одноразовое композиционное исключение. Не плодить новые сущности для косметической перестановки.
4. **Draft:** при системном назначении создать `candidate` **с первого реального применения**, даже если пока нигде больше не используется. В реестре указать, что это рабочее предложение; не считать его принятым.
5. **Verify:** проверить применимые состояния, тексты, а11y/клавиатуру/touch, mobile-first, desktop, визуальную иерархию и соседние области; результат `verified` только при фактической проверке.
6. **Reuse / iterate:** после прохождения проверки разрешено техническое повторное использование *в границах принятого system intent*, не переводя компонент в `approved_by_user`. Неутверждённое художественное решение остаётся `proposed` и может быть изменено при арт-ревью.
7. **Checkpoint sync:** на контрольной точке записать изменения в живой UI Kit и GitHub, указать версии, охват, использующие блоки, исключения, результаты проверок и открытые художественные решения.

**Критерий promotion (purpose):** (a) ясная задача/роль, (b) повторно применимая структура или взаимодействие, (c) граница с существующими компонентами, (d) состояния и адаптивная логика могут быть заданы. Это **качественный тест**, не требование второго экземпляра. Если тест не выполнен — локальная композиция/гипотеза вне системной библиотеки; её можно позже пересмотреть.

## 4. Три класса изменения и полномочия

| Класс | Пример | DIS может самостоятельно | Когда нужно явное решение человека |
| --- | --- | --- | --- |
| **Patch** — исправление без смены намерения | Переполнение, неверное hover/focus, сломанный перенос, исправление несоответствия токену | Да, с проверкой затронутых экранов и отсутствия регрессий | Если «исправление» заметно меняет ранее принятое художественное решение |
| **Minor** — совместимое дополнение | Новый variant/status, новое состояние, новый компонент в принятой системе | Да, как `proposed` или технически `verified`, при наличии QA и сохранении дизайна | Если дополнение создаёт новую существенную визуальную идею/UX-поведение или меняет утверждённые решения |
| **Major** — изменение системы | Новая типографическая шкала, смена принципа сетки, палитры, композиционного/интерактивного языка | Может самостоятельно подготовить сравнение и кандидата, **не** распространять его как принятое изменение | Обязательно — до замены глобального baseline или массового изменения утверждённых блоков |

**Классификация Patch/Minor/Major не является разрешением** молча менять согласованную концепцию. Художественная существенность важнее технического названия версии. При сомнении: локальное исключение или `proposed` до решения человека.

## 5. Разделяем статус по трём осям

| Ось | Примеры | Что доказывает |
| --- | --- | --- |
| **Техническая/компонентная зрелость** | `candidate → verified → reusable`, `deprecated` | Компонент описан, проверен, пригоден для применения, выведен из использования. **Не** художественное принятие |
| **Художественное решение** | `proposed → ready_for_approval → approved_by_user`, `rejected / superseded` | Человек принял конкретную визуальную/поведенческую спецификацию (либо она ещё ожидает принятия) |
| **Артефакт / фактическая проверка** | `draft/coded/delivered`, `not_checked/functional_verified/fidelity_verified` | Что изготовлено и **чем реально проверено**. Совместимо с [instruction-precedence](instruction-precedence.md) |

Компонент может быть **`verified + proposed`**: работает, но ещё не художественно принят. Может быть **`reusable + proposed`** для рабочих непринятых частей текущей концепции: переиспользование разрешено только *как рабочая гипотеза*, не как защищённый художественный стандарт.  
Если арт-директор утверждает целую композицию, её конкретные показанные элементы считаются принятыми лишь **в явно согласованном объёме**; скрытые состояния и не показанные варианты не получают автоматического `approved_by_user`.

## 6. Версии, зависимости и проверки

У проекта — версия живого UI Kit и запись каждой содержательной правки компонента с `component_id`, `version`, `change_class`, `reason`, `affected_sections`, `verification`, `decision_status`, `checkpoint`. Реестр показывает `used_in`, чтобы изменения не терялись в других блоках.

- **Patch:** сверить все известные места применения, responsive и затронутые состояния.
- **Minor:** проверить новый вариант и регрессии в местах переиспользования; базовый вариант должен сохраниться.
- **Major:** подготовить влияние на типографику/сетку/связанные блоки и получить решение арт-директора перед миграцией принятого baseline.
- **Deprecation:** отметить замену/причину и список используемых мест; не удалять компонент, пока активные потребители не мигрированы или не отмечены как исключения.
- **Source of truth:** `approved_by_user` версии защищены от несанкционированной замены; `proposed` могут меняться во внутренней работе, с отслеживанием значимых рисков.

## 7. Checkpoints: когда фиксировать в GitHub

**По умолчанию:** (1) готов Seed UI Kit; (2) принята существенная художественная концепция и подготовлен Consolidated UI Kit; (3) завершена значимая группа секций/шаблонов; (4) согласовано системное Major-изменение; (5) handoff/release. Не надо создавать новые контрольные точки после каждой кнопки или микроправки.

На checkpoint DIS в ходе **активной задачи** актуализирует один UI Kit и журнал, проверяет зависимости и коммитит пакет изменений в GitHub, когда репозиторий доступен. Не обещать фонового мониторинга: без работающей задачи ничего само по себе не синхронизируется. Если GitHub недоступен — подготовить изменения локально, явно сообщить статус, не заявлять о выполненном коммите.

**Минимальная запись:** `checkpoint_id · kit_version · added/modified/deprecated · component_ids · class · used_in · QA/evidence · unresolved approvals · repo commit`. Для совместимых технических обновлений согласование каждой записи не требуется; для Major требуется предварительное художественное решение.

## 9. Проверка гипотезы

В пилоте учитывать: сколько элементов переиспользовали, сколько новых компонентов создано без необходимости, сколько системных регрессий и согласований произошло, сколько раз пришлось мигрировать компонент. Не объявлять экономию времени доказанной без наблюдений. Не создавать дополнительную бюрократию и параллельные реестры.
