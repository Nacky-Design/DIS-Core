# DIS — Skill Execution Standard · v1.0

**Решение:** 26.10.2026. **Применимость:** все новые исполняемые skills DIS; старые методики переводить по результатам аудита, не объявлять их автоматически протестированными. **Приоритет:** [instruction-precedence](instruction-precedence.md). Термины «скилл» (операционный контракт) и «реализованная автоматизация» (проверяемое ПО) **не взаимозаменяемы**.

## 1. Обязательный контракт каждого скилла

Скилл содержит 10 секций, отвечающих на разные вопросы:

1. **Trigger + applicability:** точные события запуска; когда запуск запрещён/излишен; переиспользование утверждённой области.
2. **Inputs + source of truth:** требуемые факты, защищённые тексты, статусы принятых решений, происхождение данных; что отсутствует.
3. **Dependencies:** предшествующий обязательный результат, версия актуального UI Kit/брифа и иной применимый skill.
4. **Procedure:** нумерованные исполнимые шаги, ветвления и критерии выхода из каждого шага; не ограничиваться глаголами «изучить/улучшить».
5. **Tools + observed capabilities:** конкретные доступные инструменты и границы; нет инструмента — нет заявления, что действие выполнено.
6. **Output schema:** имена полей, статусы, формат/идентификатор полученного артефакта, ссылка на фактическое доказательство.
7. **Acceptance criteria:** проверяемые условия PASS/FAIL, явно отделённые от эстетического judgement; отсутствие доказательства означает `not_verified`, не PASS.
8. **Failure handling:** локальная повторная попытка, альтернативный маршрут, `blocked` по действительно существенному внешнему препятствию; не галлюцинировать.
9. **Persistence + provenance:** что, в каком состоянии, куда и когда записано; что можно повторно использовать; права на чужие изображения.
10. **Tests + boundary cases:** ожидаемые результаты для обычного, пограничного и негативного случая; ручная экспертная оценка отдельно от машино-проверяемого результата.

Скилл с пропущенным обязательным разделом — `spec_incomplete`, без подтверждённого теста — `specified_not_validated`. Реализация `implemented` только при существующем инструменте, `verified` только после реального запуска тестов.

## 2. Классы требований

- `HARD`: источник истины, авторство и права, точный контент, запись событий, условия состояний, согласованные пользовательские решения. Исполнять буквально; FAIL блокирует ложную готовность.
- `JUDGEMENT`: художественная композиция, неожиданный перенос, качество синтеза. Не притворяться машинно объективным рейтингом; приводить сравнение, свидетельства и ограничения.
- `EXPERIMENT`: начальные пороги зрелости (150/8/20/15), художественный балл и влияние новых методик на число итераций. Проверяем на пилоте, не описываем как научно доказанное число.

## 3. Сквозной автомат состояний

`not_started → working → ready_for_check → passed / needs_work / blocked_by_essential_input / not_verified`.

- `passed`: все HARD-предусловия и соответствующие критерии выхода удовлетворены, с доказательствами.
- `needs_work`: агент может устранить неполноту самостоятельно; не спрашивать человека, чтобы заменить недоработку.
- `blocked_by_essential_input`: есть конкретное непередаваемое полномочие/художественный выбор, который нельзя вывести из текущего решения пользователя, контракта и проверенных данных; запустить [Decision Dialogue](decision-dialogue.md).
- `not_verified`: выполнена текстовая методика, но соответствующий инструмент/проверка отсутствуют. Нельзя писать `implemented` или `passed`.

Не смешивать принятие человеком, готовность артефакта, качество проверки и статус автоматизации; [instruction-precedence](instruction-precedence.md).

## 4. Единая минимальная запись выполнения

```json
{
  "skill_id": "reference-intelligence",
  "scope": "anonymized internal pilot/A2",
  "run_id": "project-checkpoint-id",
  "inputs": ["source-id@version"],
  "status": "working",
  "decision_class": "HARD|JUDGEMENT|EXPERIMENT",
  "evidence_refs": [],
  "outputs": [],
  "failed_checks": [],
  "persistence_status": "not_connected",
  "next_action": "continue|fix|request_material_choice|checkpoint"
}
```

Не заполнять неизвестные доказательства вымышленными ссылками. Не создавать отдельную презентацию об исполнении: хранить эту запись в одном существующем листе решений/логе проекта.

## 5. Общая политика эскалации

При существенной **развилке художественного решения**, а не обыкновенной неопределённости агента, использовать [Decision Dialogue](decision-dialogue.md) на **любом этапе**. DIS сначала готовит обоснованную рекомендацию. Человек может выбрать **несколько совместимых** направлений; выбор не равен разрешению смешать заведомо несовместимые альтернативы. Выбор становится источником знания Studio Signature только в корректном статусе и границах, без автоматического утверждения фирменного стиля.
