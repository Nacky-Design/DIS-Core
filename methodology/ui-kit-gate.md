# DIS — UI Kit Gate / живой набор визуальных правил · pilot v0.1

**Статус:** обязательный системный checkpoint для визуального производства; минимальный состав зависит от масштаба проекта.  
**Основание:** пилот anonymized internal pilot, 25.10.2026. Развивает [Design System Continuity](design-system-continuity.md), а не заменяет его.

## Что было пропущено

Текстовый System Design Contract уже описывает типографику, сетку и компоненты. Но без **материального UI Kit** агент может в каждом блоке заново задавать H2/H3, body, радиусы, кнопки и состояния. Результат — стилевые регрессии, визуальные дубли и «SaaS из карточек».

**UI Kit — обязательный проверяемый артефакт внутри существующего System Design Contract.** Он бывает Figma-компонентами, HTML/CSS story page, токенами + браузерным preview или другим форматом выбранного маршрута. Нельзя считать текстовое обещание «шрифты согласованы» готовым UI Kit.

## Два момента фиксации

**Seed UI Kit (до дорогой визуальной итерации/масштабирования).** Как только есть принятый художественный ориентир или исходный UI:
- Собрать *только реально применимые* предварительные `typography / layout / colors / surfaces / radii / controls`.
- Указать статус значения: `source-verified`, `proposed`, `approved_by_user` или `exception`.
- Показать хотя бы одну mobile и одну desktop реализацию типографической иерархии в реальном масштабе.
- Визуальная проба допустима с `proposed` токенами, но её элементы не автоматически становятся утверждённой системой.

**Consolidated UI Kit (после принятой концепции, ДО тиражирования секций/шаблонов).** Уточнить реальные токены и живые компоненты; сверить с соседними блоками. Не передавать отдельный успешный блок в масштабное производство без этой фиксации.

## Минимальный состав

| Группа | Нужное доказательство |
| --- | --- |
| **Typography** | Семейство + кириллица, font-weight, роли display/H1/H2/H3/body/lead/UI/metadata/CTA, размеры, line-height, ограничения строк, mobile/tablet/desktop; токены вместо случайных размеров по блокам |
| **Layout** | Две внешние оси, max/min widths где оправдано, сетка, отступы секций, ритм и правила адаптации |
| **Colors / surfaces** | Фон, текст, акцент, бордер/разделитель, hover/active/focus/disabled, контраст и осмысленность выделения |
| **Primitives** | Кнопки, ссылки, поля, карточки, вкладки/аккордеоны, метки, иконки, статусы — лишь используемые в проекте |
| **Domain components** | Для медпроекта: карточка записи, результаты анализов, очередь задач и другие реально показанные UI; достоверное содержание, базовое состояние и доступные действия |
| **States / responsive** | Default, hover (где есть), focus, active, expanded, error, empty и mobile/touch — применимые состояния и демонстрация |
| **Ownership / exceptions** | ID компонента, где используется, версия/статус, источник, объяснение намеренных исключений |

**Не путать минимальный текст и весь текст:** локальный порог читаемости 16 px (если принят в проекте) — **минимум**, а не `body = lead = caption = 16`. Разницу иерархии между секциями проверять в живом preview.

## Согласованная модель управления: C · purpose · checkpoint

**Управляемая автономия (C):** DIS самостоятельно создаёт, проверяет и повторно использует UI-компоненты в рамках принятого дизайна; существенные изменения утверждённой визуальной системы согласуются с арт-директором. **Purpose:** компонент попадает в рабочий UI Kit уже при первом применении, если понятны его функция и потенциальная повторная применимость; не требуется ждать второго использования. **Checkpoint:** GitHub обновляется пакетом при контрольных точках проекта, не после каждой мелкой правки.

Техническая зрелость компонента (`candidate/verified/reusable`) и художественное принятие (`proposed/approved_by_user`) — разные статусы. Рабочий проверенный компонент не считается автоматически художественно утверждённым. Подробные правила классов Patch/Minor/Major, исключений, версий, проверок зависимостей и синхронизации: **[UI Kit Evolution Protocol](ui-kit-evolution.md)**.

## Непрерывное обновление

1. Перед каждым новым визуальным блоком — брать актуальные токены/компоненты, не создавать параллельный набор.
2. Если появляется новый повторяемый паттерн, сначала проверить, нельзя ли использовать существующий; иначе добавить *один* новый компонент с состояниями и ролью. Разовое художественное исключение записывать без насильственного превращения в компонент.
3. После принятия системного изменения обновить kit и проверить соседние / зависимые секции, не менять утверждённый дизайн молча.
4. До Visual Quality Gate убедиться, что все использованные типографические роли и основные UI-компоненты имеют соответствие kit или записанное исключение.
5. До release проверять, что HTML/Figma воспроизводит те же значения; токены без реально проверенного рендера не являются доказательством.

**Минимальный результат:** один живой UI-kit в контексте проекта + ссылка на него из листа решений. Не требовать огромной дизайн-системы до первой художественной идеи; набор растёт по мере фактических потребностей.

Применять также [Visual Quality Gate](visual-quality-gate.md) перед художественным показом.
